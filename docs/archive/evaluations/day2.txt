
# Day 2 Alphabot Evaluation & Sprint Retrospective

## 1. Session Objective
The primary goal was to implement the feature-complete "Real-Time Stream-Parsing Chatbot" based on the provided Product Requirement Document (PRD). This involved building a full-stack application with a Next.js frontend and a Python/FastAPI backend.

## 2. Progress & Milestones Achieved
A full-featured prototype was successfully built, including:
- **Project Scaffolding:** Frontend and backend project structures were created.
- **Database Generation:** A script to generate a large (250k rows) synthetic SQLite database was implemented and run.
- **Real-Time Frontend Parser:** A sophisticated client-side engine was developed using a Trie data structure to parse user input in real-time, classifying words into types (`ACTION`, `METRIC`, `DIMENSION`, etc.).
- **Query Blueprint:** The frontend successfully generates a structured JSON "Query Blueprint" from the user's raw query.
- **Dynamic UI:** A dark-themed UI was implemented to display classified tokens, performance metrics, the query blueprint, and data visualizations.
- **Visualization Layer:** A charting component was created to dynamically render Bar, Line, and Donut charts, as well as single KPI values, based on the query results.
- **Architectural Upgrades:** The engine was significantly upgraded to handle complex logic, including multi-word terms, date ranges, and mathematical comparisons (`less than`, `greater than`).

## 3. Critical Bugs & Failures Encountered
The session was dominated by a series of persistent, cascading bugs that prevented the application from functioning correctly.

- **Initial Hydration & Server Stability:** The development environment was unstable, with "zombie" server processes causing port conflicts and frontend crashes. This was eventually resolved by manually killing the lingering processes.
- **Flawed SQL Generation ("Values Only" Bug):** The most critical application logic bug. The backend's query processor had flawed logic that incorrectly defaulted to `SELECT SUM(...)` or added a `GROUP BY` clause for simple filtered queries. This caused queries like *"what is the revenue for sales"* to return data for all departments instead of a single value.
- **The "Clarification Required" Loop:** A bug in the backend's "Fail-Fast" validation logic, combined with the above issue, caused the system to incorrectly ask for clarification on perfectly valid queries.
- **The True Root Cause (Discovered Late):** The backend was architecturally flawed. It was completely **ignoring the excellent blueprint generated by the client** and calling the Ollama LLM on every query. The LLM would then fail to parse the complex query, returning invalid JSON. My code would then mishandle this LLM failure, leading to a crash.

## 4. Final Diagnosis & Next Steps
- **Current State:** The application is **non-functional**. The last set of fixes to correct the core architectural flaw (to trust the client blueprint first) have not been successfully applied due to repeated environmental and tooling failures.
- **Root Cause Summary:** A combination of an unstable development environment and a critical architectural flaw in the backend's request handling logic.
- **Recommended Next Action:** As discussed, the only reliable path forward is to **rebuild the backend logic from a single, clean, and correct script**. This will eliminate all legacy bugs from the failed patch attempts and correctly implement the "client-first, LLM-as-fallback" architecture.

## 5. Ollama Model Analysis & Recommendation
Based on the available local Ollama models:

*   **Current Model:** `llama3.2:latest`
*   **Recommendation:** Switch to **`phi3.5:3.8b`**

**Justification:**
While `llama3.2` is a capable model, its performance in consistently generating perfectly structured JSON output for our complex queries has been a point of failure. `phi3.5:3.8b` (Microsoft's Phi-3.5) has a strong reputation for its instruction-following abilities and reasoning capabilities, particularly for its compact size. Leveraging a model specifically known for these strengths is a logical step to improve the reliability of our AI fallback mechanism.

This change, combined with the planned backend rebuild, is the best path forward to achieve a resilient, production-ready system.

Once the backend is rebuilt, the application should finally function as intended.
